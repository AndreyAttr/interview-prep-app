## Key decisions

- Data-model conflicts between the two spec docs resolved in favor of `section2-cc.md` (see CLAUDE.md's conflict rule).
- Component/file naming follows this Angular CLI version's convention: no `.component.ts` suffix, class names without a `Component` suffix (e.g. `shell.ts` → `export class Shell`).
- `provideAnimationsAsync()` and the `@angular/animations` package were missing from the initial scaffold and had to be added — required for any Angular Material component to work.
- **Category tree built without Angular CDK Tree/DragDrop**, despite section2-cc.md naming them as the intended approach: the required interactions (zone-based before/inside/after drop targeting, questions rendered as non-model rows under a category, special/undraggable nodes) didn't map cleanly onto CDK Tree's data-source model or `CdkDropList`'s reordering-only behavior, and `Version 2.html`'s actual working implementation uses plain native drag events, not a drag-and-drop library. The component instead builds the nested view from the flat list itself (`buildTree`/`flattenVisible`) and handles drag state with signals + native `dragstart`/`dragover`/`drop` — functionally equivalent to the spec's requirements, just not the literal named APIs.
- **Category Settings modal uses component-local signals, not `ReactiveFormsModule`** (also named in section2-cc.md): no other part of the app uses Reactive Forms, and the modal's actual requirements (a few plain fields plus the already-built signal-based `WeightedSliders`) didn't need FormGroup/FormControl machinery to satisfy the same behavior (dynamic `sourceWeights` field appearing only for `questionSource === 'mix'`, live sum validation).
- **Angular's required `input()` cannot be read in a field initializer or the constructor** — the compiler statically forbids it (`NG8118`)/it throws at runtime (`NG0950`) because the input isn't guaranteed set yet at that point. Discovered while building `CategorySettingsModal`, which needed to seed its editable state from `@Input() category`'s existing settings. Fix: derive initial values via `computed()` (evaluated lazily, after Angular has set the input), not eagerly in the constructor.
- **Signal-backed mock services must be consumed via their public `readonly` signal, not by re-wrapping their `getXxx(): Observable<T>` method in `toSignal()`.** The `Observable` methods return `of(this.state())` — a one-time snapshot, not a live stream — so a `toSignal(getXxx())` subscription freezes at whatever the state was when the subscribing component was created and silently never updates again. This caused the category-tree Star/Save bug (see Done above). Any new component reading mock-service data going forward should use the service's own signal property directly.
- **HTML `<table>` needs `table-layout: fixed` (plus explicit column widths) to actually enforce a minimum column width** — with the default `auto` layout, the browser will shrink a `width`-styled `<td>` (e.g. the History table's 220px Actions column) below its stated width if other columns need the space, which would silently violate HANDOFF-CC.md §8.7's "Actions column ≥220px, no wrapping" requirement.
- **Dashboard bar chart built as a hand-written inline `<svg>` in the template**, despite section2-cc.md suggesting `ngx-charts`/Chart.js: the chart is a simple fixed set of proportional bars with no interactivity (tooltips, zoom, legends beyond a static 3-item key) required by HANDOFF-CC.md, so a charting library would add a dependency and theming-integration work for no behavior the app actually needs. Matches this project's existing pattern of using `Version 2.html`'s actual working implementation as the reference over a spec doc's suggested library when the two diverge (same reasoning as the category tree's native drag-and-drop over CDK Tree/DragDrop).
- **Dashboard reuses existing theme tokens (`--success`, `--status-partial`, `--danger`, `--bg4`) for score-based coloring** instead of the prototype's hardcoded hex values (`#22c55e`/`#f59e0b`/`#ef4444`) — those tokens already resolve to equivalent colors in both themes and are the app's established pattern (e.g. History's score bar already uses `--success`), so hardcoding hex would have created a second, unsynchronized source of the same colors.
- **`ThemeService` is injected in the root `App` component, not left to be picked up incidentally by whichever page happens to render first.** Angular's DI only runs a service's constructor the first time it's actually injected somewhere — `ThemeService`'s `data-theme` attribute logic lived entirely in that constructor, so it silently never ran on any route that doesn't render something inside `Shell` (i.e. `/login`). Any future route added outside the shell inherits this fix for free since it's now at the app root; a new *service* with side effects that must run app-wide (not just theme) should follow the same pattern — inject it in `App`, don't assume some other component will happen to need it first.
